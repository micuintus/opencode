# PART I — VISION

## 1. The Four Pillars

micuDAC is built on four converging insights from industry leaders who independently arrived at the same conclusion: **stop fighting LLM non-determinism — separate what code does well from what AI does well.**

### Pillar 1: The Manus Insight — Everything Is Text

A [former backend lead at Manus](https://coding4food.com/en/post/ex-manus-lead-drops-function-calling-for-unix-cli-ai-agents) (1600+ upvotes on r/LocalLLaMA) revealed that after 2 years building production agents, they **stopped using function calling entirely**. Replacement: a single `run(command="...")` surface backed by Unix CLI.

> "50 years ago, Unix creators made a core decision: everything is a text stream. LLMs think in text, act in text, consume text."

**Key insights:**
- **Tool sprawl kills agents**: "Once an agent has to choose between twenty, forty, or eighty overlapping tools, the very act of choosing becomes part of the failure surface."
- **Models are already CLI experts**: trained on billions of shell commands from GitHub/StackOverflow — "it's already the ultimate terminal power user."
- **Progressive help discovery**: don't bloat system prompts; commands self-document via help text.
- **Error messages must include fixes**: not just "error" but `[error] binary image. Use: see photo.png`.
- **Compact grammar wins**: one pipeline composes what would take multiple tool calls.

**How micuDAC extends this:** `oc` IS the Manus approach, but deeper. Manus has `run(command)`. We have `run(command that calls back to the AI)`. The LLM writes shell pipelines that include AI judgment at decision points. Manus stopped at CLI execution. We add the callback loop.

### Pillar 2: Deterministic vs Non-Deterministic Separation

**LLMs are unreliable at deterministic execution** — they lose count in loops, forget state across turns, apply transformations inconsistently, hallucinate completed actions.

**Code is perfectly reliable at deterministic execution** — a for loop runs exactly N times, a variable holds state perfectly, a tool call applies exactly what's specified.

**LLMs are brilliant at non-deterministic judgment** — "Is this buggy?", "What's the fix?", "Does this need migration?"

**micuDAC makes this separation concrete in the API:**
- `oc tool edit/write/read` → deterministic, no LLM, reliable, fast
- `oc prompt "question"` → non-deterministic, LLM judgment, where AI excels

This is not just cheaper — **it is more reliable.**

**Validated by Anthropic's PTC:** 37% token reduction, accuracy improvements (46.5% → 51.2%) with the same thesis. But PTC is API-only/cloud-only/Claude-only. micuDAC is CLI-native, local, and model-agnostic.

### Pillar 3: The Ralph Loop Philosophy

The [Ralph Loop](https://ghuntley.com/loop/) (Geoffrey Huntley, 2024) is the most influential pattern in agentic coding for 2025-2026. Its philosophy embraces LLM fallibility:

> "The technique is deterministically bad in an undeterministic world."

**Core principles:**
- **Code as state**: Progress lives in files and git history, not LLM context
- **Machine-verifiable criteria**: Success = tests pass, not "the LLM says it's done"
- **Fresh context rotation**: Each iteration starts clean, avoiding context pollution
- **External verification**: The loop checks objective reality (test results, file state), not LLM self-assessment
- **Monolithic simplicity**: One task per loop, not complex multi-agent choreography

**How micuDAC enables Ralph Loops:**

```bash
# A Ralph Loop, generated by the LLM, running inside openCode:
for attempt in $(seq 1 20); do
    output=$(npm test 2>&1)
    [ $? -eq 0 ] && echo "PASS after $attempt attempts" && break
    echo "$output" | oc prompt "Fix these failures. Use oc tool edit to make changes."
    # Each oc prompt = fresh child session = clean context
    # Progress persists in files, not in LLM memory
done
```

**Key insight:** micuDAC makes the LLM the AUTHOR of Ralph Loops, not just the executor. The LLM designs the loop structure, chooses verification criteria, and decides when to use fresh context — all expressed in deterministic bash.

### Pillar 4: The Fabric Pattern — AI in the UNIX Pipe

[Fabric](https://github.com/danielmiessler/Fabric) (Daniel Miessler, 40k+ stars) proves the AI-in-the-pipeline model works:

```bash
yt --transcript https://youtu.be/... | fabric -sp extract_wisdom
```

**Core principles:**
- **AI as a UNIX pipe**: text in, text out, composable
- **Patterns as reusable prompts**: task-specific AI calls, not monolithic conversations
- **CLI-first**: the command line is the integration layer
- **"AI isn't a thing; it's a magnifier of a thing"**

**How micuDAC is Fabric-for-agents:** Fabric gives HUMANS a way to pipe data through AI. micuDAC gives the AI AGENT itself the same power:

```bash
# Fabric-style patterns, but the LLM writes them at runtime:
cat src/auth.ts | oc prompt -s "Security auditor. OWASP Top 10." "Audit this"
git diff HEAD~5 | oc prompt "Summarize changes for release notes"
find src/ -name "*.ts" | while read f; do
    cat "$f" | oc prompt -s "Code reviewer" "Rate complexity 1-10. Just the number."
done | sort -rn | head -10
```

## 2. The Synthesis

micuDAC = **Manus CLI philosophy** + **deterministic/non-deterministic split** + **Ralph Loop engine** + **Fabric composition** + **openCode tool ecosystem**

| Concept | Manus CLI | Ralph Loop | Fabric | micuDAC |
|---|---|---|---|---|
| Core idea | Everything is text | Embrace fallibility | AI in the pipe | **All four** |
| Who writes it? | Human configures | Human writes loop | Human writes pipe | **The LLM** |
| AI interface | `run(command)` | External LLM call | `fabric -sp pattern` | `oc prompt` + `oc tool` |
| Determinism | Shell commands | bash + tests | UNIX pipes | `oc tool` + bash |
| Verification | Exit codes | Tests, git | Human reads | `oc tool` + tests |
| Context mgmt | Single run | Fresh rotation | Stateless pipe | Fresh child session |

**The LLM becomes a meta-programmer**: it writes the program that orchestrates itself. It has the Manus insight (CLI over function calling), the Ralph Loop pattern (retry until verified), Fabric's composition (pipe through AI), and openCode's full tool ecosystem.

## 3. Ecosystem Integration

### 3.1 What the LLM Can Orchestrate via `oc`

The `oc` command gives the LLM's scripts access to the FULL openCode ecosystem:

**Subagent orchestration:**
```bash
analysis=$(oc agent explore "Find all files affected by this change")
echo "$analysis" | oc prompt "Create a test plan"
```

**Todo management (deterministic, no LLM):**
```bash
oc todo add "Step 1: Find affected files"
oc todo add "Step 2: Generate tests"
# ... later:
oc todo done 1
```

**Direct tool calls (deterministic, no LLM):**
```bash
content=$(oc tool read src/auth.ts)
oc tool edit src/auth.ts --old "oldAPI()" --new "newAPI()"
matches=$(oc tool grep "deprecated" src/)
files=$(oc tool glob "src/**/*.test.ts")
```

**AI judgment (non-deterministic):**
```bash
echo "$content" | oc prompt "Is this code safe?"
echo "$test_output" | oc prompt -s "QA engineer" "Analyze failures"
```

**Dynamic specialists:**
```bash
oc prompt -s "Database migration expert" "Review this schema change"
oc prompt -s "Security auditor" "Check for OWASP Top 10"
```

**Multi-model cost optimization:**
```bash
cheap=$(oc prompt -m anthropic/claude-haiku-4-5-20251001 "Relevant? yes/no")
# Only use expensive model when needed
```

**Python for computation:**
```bash
python3 << 'PY'
import subprocess, json
result = subprocess.run(["oc", "tool", "read", "data.json"], capture_output=True, text=True)
data = json.loads(result.stdout)
for item in data:
    item["expected"] = item["value"] * 2 + 1  # Python computes, reliably
print(json.dumps(data))
PY
```

### 3.2 Sophisticated Patterns

**Ralph Loop with external verification:**
```bash
for attempt in $(seq 1 20); do
    npm test 2>&1 && break
    npm test 2>&1 | oc prompt "Fix failures. Use oc tool edit."
done
```

**Map-reduce over files:**
```bash
find src/ -name "*.ts" | while read f; do
    score=$(cat "$f" | oc prompt -m fast "Complexity score 1-10. Just the number.")
    echo "$score $f"
done | sort -rn | head -10 | oc prompt "Most complex files. Suggest refactoring priorities."
```

**Bisect a regression:**
```bash
for sha in $(git log --oneline -50 | awk '{print $1}'); do
    git checkout "$sha" 2>/dev/null
    if npm test 2>&1 >/dev/null; then
        echo "Last good: $sha"
        git checkout - 2>/dev/null
        git show "$sha" | oc prompt "This commit broke things. Explain why."
        break
    fi
done
```

**Pipeline with todo tracking and verification:**
```bash
oc todo add "Extract requirements"
oc todo add "Generate code"
oc todo add "Run tests"
oc todo add "Review"

spec=$(oc tool read requirements.md)
oc todo done 1

echo "$spec" | oc prompt "Implement this. Use oc tool write for each file."
oc todo done 2

result=$(npm test 2>&1)
[ $? -ne 0 ] && echo "$result" | oc prompt "Fix test failures"
oc todo done 3

git diff | oc prompt -s "Senior engineer. Be critical." "Review these changes."
oc todo done 4
```

## 4. Built-in Guidance: Graded Examples + Verification + State

**Design principle:** No external skills or frameworks required. Everything built into the  `<algorithmic-tasks>` block in `system.ts`. Minimal but effective.

**Research basis:** Tang et al. (2025) — performance peaks at 5-20 examples, then declines. We target 4 graded examples (simple → sophisticated) plus verification guidance and state tracking pattern.

### 4.1 The Guidance: 39 Lines, 3 Paradigms, 12 Capabilities

**Design principles:**
- Teach COMPOSITION, not rigid patterns — "combine freely" enables creativity
- Organize commands by deterministic/non-deterministic — embeds the mental model
- Three examples = three paradigms (iteration, retry, pipeline) — any sophisticated script is a combination
- MUST language for verification (Amatriain 2024: "MUST" > "should")
- Failure is recoverable — "fix and retry" (Ralph Loop philosophy)

All guidance lives inside the `<algorithmic-tasks>` XML block in `SystemPrompt.environment()`,  behind ``.

### 4.2 The Final Guidance Text (exact implementation)

```
<algorithmic-tasks>
When a task involves iterating over many items (>5), retrying until success,
or multi-step pipelines, write a bash script instead of calling tools one by one.

Inside bash, `oc` separates deterministic operations (reliable, no LLM) from
AI judgment (non-deterministic):
  oc tool read <path>                 — Read file → stdout (deterministic)
  oc tool write <path>                — Write stdin → file (deterministic)
  oc tool edit <path> --old x --new y — Edit file (deterministic)
  oc tool grep "pattern" <path>       — Search → stdout (deterministic)
  oc tool glob "pattern"              — Find files → stdout (deterministic)
  oc prompt "question"                — AI judgment → stdout (non-deterministic)
  oc prompt -s "role" "question"      — Dynamic specialist (non-deterministic)
  oc todo add "item"                  — Track progress (deterministic)
  oc agent explore "task"             — Spawn subagent (non-deterministic)
  cat file | oc prompt "analyze"      — Pipe context via stdin

Simple — deterministic batch, no AI:
  for f in $(oc tool glob "src/**/*.ts"); do echo "$(oc tool read "$f" | wc -l) $f"; done | sort -rn

Comprehensive — retry loop with progress, specialists, and verification:
  oc todo add "Identify failures"
  oc todo add "Fix each failure"
  oc todo add "Verify all pass"
  output=$(npm test 2>&1)
  oc todo done 1
  echo "$output" | oc prompt "List failing test files only, one per line" | while read f; do
      oc tool read "$f" | oc prompt "Fix this test ($f). Use oc tool edit."
  done
  oc todo done 2
  for attempt in $(seq 1 3); do
      npm test 2>&1 && echo "All passing!" && break
      npm test 2>&1 | oc prompt -s "Debugging specialist" "Try a different approach."
  done
  oc todo done 3

Advanced — pipeline and map-reduce:
  oc tool grep "TODO" src/ | oc prompt "Categorize by urgency" | oc tool write report.md

  for f in $(oc tool glob "src/**/*.ts"); do
      oc tool read "$f" | oc prompt "One-line summary"
  done | oc prompt -s "Architect" "Describe the system architecture"

You MUST verify before executing: loops terminate, oc syntax correct, errors handled.
If a script fails, fix the error and retry — oc returns clear error messages.
IMPORTANT: Set timeout: 600000 or higher for scripts using oc.
For computation, use python3 — oc commands work from any language.
These are composable primitives — combine freely based on the task.
</algorithmic-tasks>
```

### 4.3 What the Three Examples Teach

| Example | Paradigm | Capabilities Shown |
|---|---|---|
| **Simple** (1 line) | Iteration | `oc tool glob`, `oc tool read`, bash pipe, `sort`, no AI |
| **Comprehensive** (12 lines) | Retry/Ralph Loop | `oc todo`, `oc prompt`, `oc prompt -s`, `oc tool read`, pipe, while loop, retry, multi-stage |
| **Advanced** (5 lines) | Pipeline + Map-reduce | `oc tool grep`, `oc prompt`, `oc prompt -s`, `oc tool write`, pipe chain, loop→synthesize |

**12 capabilities in 39 lines:**
1. Deterministic tools (read/write/edit/grep/glob) — command reference
2. AI judgment (oc prompt) — comprehensive + advanced
3. Dynamic specialist (oc prompt -s) — comprehensive + advanced
4. Progress tracking (oc todo) — comprehensive
5. Subagent dispatch (oc agent) — command reference
6. Pipe composition — all three examples
7. Deterministic batch — simple example
8. Ralph Loop (retry + verify) — comprehensive
9. Multi-stage pipeline — comprehensive (3 todo stages)
10. Pipeline transform chain — advanced (grep→AI→write)
11. Map-reduce — advanced (per-file→synthesize)
12. Composition principle — "combine freely" line

### 4.4 Verification Design

**MUST language** (Amatriain 2024): `"You MUST verify before executing"` — assertive, not advisory.

**Failure recovery** (Ralph Loop): `"If a script fails, fix and retry"` — tells the LLM failure is normal and recoverable. Without this, the LLM might avoid writing scripts.

**What happens when scripts break:**
| Failure | Recovery |
|---|---|
| Syntax error | bash catches → error output → LLM fixes |
| Wrong oc syntax | oc HTTP error check → clear message → LLM fixes |
| Logic error | External verification (test results) catches it |
| Infinite loop | bash timeout kills it → "timeout exceeded" message |

### 4.5 Model Aliases (-m fast/strong)

**Dropped for now.** Orthogonal feature. `-m` works with full model IDs. Aliases need config schema changes. Core value comes from det/non-det split, not model selection.

### 4.6 Python

**One-line hint only.** `"For computation, use python3 — oc commands work from any language."` Full Python templates belong in an optional orchestration skill.

### 4.7 Future: Orchestration Skill (optional, additive)

For users wanting MORE patterns beyond the built-in 3, `.opencode/skills/orchestrate/SKILL.md`:
- Bisect regression template
- Conditional branching (AI decides the path)
- Python computation pipelines
- Multi-model cost optimization (once aliases exist)
- Self-healing adaptive loops

Additive — micuDAC works without it.

## 6. Architecture

### Data Flow

```
openCode instance (TUI active, server on :4096)
│
├─ Session: ses_abc123
│  └─ LLM calls bash tool with a script (Ralph Loop, pipeline, etc.)
│       │
│       │  bash.ts injects: OPENCODE_SERVER_URL, OPENCODE_SESSION_ID, PATH
│       │  (only when =true && Server.url exists)
│       │
│       ▼
│  ┌─ bash script (deterministic skeleton) ────────────┐
│  │                                                     │
│  │  files=$(grep -rl "TODO" src/)         ← native    │
│  │  content=$(oc tool read "$f")          ← HTTP →────┼→ POST /session/:id/tool
│  │                                         no LLM      │   Tool.execute() directly
│  │  fix=$(echo "$content" | oc prompt "Fix") ← HTTP →─┼→ POST /session/:id/exec
│  │                                         LLM thinks  │   Creates child session
│  │  oc todo done 1                        ← HTTP →────┼→ Todo CRUD (no LLM)
│  │                                                     │
│  └─────────────────────────────────────────────────────┘
│
│  Everything routes through the SAME server instance.
│  TUI shows: bash streaming + child sessions + tool calls.
│  Abort propagation: HTTP disconnect → SessionPrompt.cancel(child)
```

### How Each Piece Works

**bash.ts (env vars + PATH):**
- Flag-gated: only when ` && Server.url`
- Injects `OPENCODE_SERVER_URL`, `OPENCODE_SESSION_ID`, and `bin/` on PATH
- Uses conditional spread: `...(condition ? { vars } : {})`

**POST /session/:id/exec (AI callback):**
1.  → 404 if disabled
2. Validates parent session exists (NotFoundError → 404)
3. Creates child session with `parentID`
4. Registers abort handler: `c.req.raw.signal → SessionPrompt.cancel(child)`
5. Calls `SessionPrompt.prompt()` with text, system, agent, model
6. Extracts last text part via `findLast`
7. Streams as `text/plain`

**POST /session/:id/tool (direct execution):**
1.  → 404 if disabled
2. Looks up tool via `ToolRegistry.get(name)` → 404 if not found
3. Gets session + agent (build) for permission merge
4. Creates `Tool.Context` with `Permission.merge(agent.permission, session.permission)`
5. Calls `tool.execute(args, ctx)` directly — NO LLM
6. Streams output as `text/plain`

**bin/oc (POSIX sh helper):**
- Routes subcommands to endpoints via `curl`
- JSON encoding via `jq` (with sed fallback)
- Body piped via stdin (`printf | curl -d @-`) to avoid ARG_MAX
- HTTP status checking: errors to stderr with return code 1
- Per-tool argument parsing for ergonomic CLI
- Trailing slash stripped from server URL

### Feature Flag Gating

Everything behind ``:
- **bash.ts:** Env vars + PATH only injected when flag is on
- **Endpoints:** Return 404 when flag is off
- **system.ts:** Prompt guidance only injected when flag is on

Enable: `=true` or `OPENCODE_EXPERIMENTAL=true`

## 7. Design Decisions

| Decision | Rationale |
|---|---|
| **Bash** (not TS/Python) | UNIX native. LLMs fluent (billions of examples). `oc` handles the hard parts (HTTP, JSON). No new dependency. Manus lead validated: "it's already the ultimate terminal power user." |
| **HTTP into running instance** | No new processes. Instant. Integrated. One TUI. Manus approach extended with callbacks. |
| **Two endpoints** (`/exec` + `/tool`) | The thesis as API: non-deterministic vs deterministic. One endpoint would conflate them. |
| **No new tool** | Bash tool already integrated (spawn, stream, timeout, abort, permissions). +9 lines to enable callbacks. |
| **Permission merge** (agent + session) | `/tool` endpoint matches normal agent loop behavior. Without it, `oc tool read/write/grep` blocked. |
| **Prompt in environment()** | All models see it (not just Claude). Flag-gated. One place. |
| **POSIX sh** | Works on any UNIX system including minimal containers. |
| **Abort propagation** | HTTP disconnect → `SessionPrompt.cancel(child)`. No orphaned sessions burning tokens. |
| **Trailing slash strip** | `Server.url.toString()` includes `/`. Without strip, double-slash routes to web UI. |

## 12. Design Journey

### How We Got Here

1. **Started with TypeScript script tool** — too complex, new tool overhead, not UNIX
2. **Considered Python** — zero Python dependency in openCode, dealbreaker for PR
3. **Considered bash + TypeScript helper** → realized openCode IS a CLI app, why create another?
4. **Realized the bash tool is already integrated** — just needs a callback mechanism
5. **`oc` emerged as a UNIX command** — text in, text out, composable via pipes
6. **Added direct tool execution** — the thesis demands deterministic ops bypass the LLM
7. **Put prompt guidance in environment()** — all models, not just Claude
8. **Feature flag** — safe to ship, zero impact when off
9. **Permission merge** — `/tool` endpoint must match agent loop behavior
10. **Trailing slash fix** — found during E2E testing, `Server.url` includes `/`
11. **Manus/Ralph/Fabric alignment** — our design independently converged with all three

### Lessons Learned

**From implementation:**
- Commit after each step, not at the end
- System prompt guidance must be 
- `z.record(z.any())` is Zod v3; v4 requires `z.record(z.string(), z.any())`
- `Server.url` deprecated — need alternative for production PR
- ARG_MAX: pipe body to curl, don't pass as argument
- `Server.url.toString()` trailing slash → double slashes → HTML responses
- Single-word variable names per AGENTS.md

**From testing:**
- `run` mode doesn't start server → needs `--attach` or TUI
- `run --attach` auto-rejects permissions → `oc tool` blocked headless
- Permission merge critical for `/tool` endpoint
- LLM DOES adopt `oc` from system prompt guidance (tested with Kimi k2.5)
- LLM correctly avoids `oc` for simple tasks
- LLM gracefully falls back when `oc` permissions rejected
- Python needed for computational pipelines — oc works from Python via subprocess
- Stronger models would likely generate better oc scripts

### 14.2 TUI Visibility — oc Calls as First-Class Citizens

**Problem**: `oc tool read` and `oc prompt` calls from bash scripts were invisible in the TUI. The user saw only a bash block with streaming text.

**Solution**: The `/tool` and `/exec` endpoints now create real ToolParts when called from a bash context (opt-in via `OPENCODE_MESSAGE_ID`).

| oc command | Visual in TUI | Mechanism |
|---|---|---|
| `oc tool read file.ts` | `→ Read file.ts ✓` | ToolPart with `metadata.oc: true` on parent message |
| `oc tool grep "pat" src/` | `→ Grep "pat" ✓` | Same |
| `oc prompt "summarize"` | `⚙ task — oc prompt ✓` + streaming text | ToolPart with `tool: "task"`, `metadata.sessionId` → child session |
| `oc agent explore "task"` | Same as prompt | Same |
| `[oc] tool read file.ts` | Dimmed text in bash block | Auto-announce to stderr |

**How it works**:
1. `bash.ts` injects `OPENCODE_MESSAGE_ID` env var (the assistant message that owns the bash Part)
2. `bin/oc.ts` sends `messageID` in HTTP request body
3. Server creates running/completed/error ToolParts → `Bus.publish(PartUpdated)` → SSE → TUI
4. For `oc prompt`: subscribes to child session's `PartDelta` events, streams text to parent ToolPart
5. ToolParts marked with `metadata.oc: true` are filtered from `toModelMessages()` (no invalid tool_use/tool_result pairing)
6. Direct API callers (no messageID) are unaffected — exact same behavior as before

**Subagent navigation**: `oc prompt` creates ToolParts with `tool: "task"` and `metadata.sessionId`, so the TUI shows "ctrl+x down — view subagents" and users can navigate into child sessions.

### 14.3 Transparent PDF/Image Piping

**Problem**: `oc tool read paper.pdf | oc prompt "summarize"` didn't work because the Read tool returns PDFs as multimodal attachments (base64), not text. The pipe only carried `"PDF read successfully"`.

**Solution**: `__oc_file__:` protocol between `/tool` and `oc prompt`:
1. `/tool` endpoint appends `\n__oc_file__:/absolute/path/to/file.pdf` when result has attachments
2. `oc prompt` detects `__oc_file__:` markers in stdin, reads the file, sends as multimodal attachment
3. Child session LLM sees the actual PDF natively

```bash
# This now Just Works:
oc tool read paper.pdf | oc prompt "Summarize this paper"
```

### 14.4 Performance Optimizations

**Compiled native binary**: `bin/oc-native` via `bun build --compile --no-compile-autoload-bunfig`
- Startup: ~40ms (compiled) vs ~190ms (interpreted) = **5× faster**
- `bin/oc` shell wrapper uses `oc-native` if present, falls back to `bun run oc.ts`
- 100 tool calls: ~4s (compiled) vs ~19s (interpreted)

**O(1) Todo.add()**: Changed from delete-all + insert-all (O(N²)) to direct INSERT. 100 todos: milliseconds instead of seconds.

**Auto-announce**: Every oc call writes dimmed `[oc] tool read src/...` to stderr, visible in TUI bash block in real-time. No LLM cooperation needed.

**Model inheritance**: `/exec` endpoint inherits parent session's model when none specified. Fixes silent failures when TUI uses a different model than config default.

### 14.5 Future: Persistent oc Daemon

**Current overhead**: Each `oc` call = process spawn (~40ms compiled). For 100 tool calls: ~4s.

**Daemon approach** (not implemented):
- Bash tool starts a lightweight daemon on a Unix socket at script start
- `oc` connects to socket instead of spawning a new process
- Per-call latency drops from ~40ms to ~1ms (IPC only)
- Daemon killed when bash tool exits

**Note**: For `oc prompt` calls, the LLM inference dominates (5-15s). The 40ms spawn is negligible. The daemon mainly helps for heavy `oc tool` loops (100+ deterministic calls). Compiled binary is sufficient for most use cases.

### 14.6 Key Bugs Fixed

| Bug | Root Cause | Fix |
|---|---|---|
| `oc prompt` returned empty output | Child session used `Provider.defaultModel()` instead of parent's model | `/exec` inherits parent session model |
| `oc tool glob` ignored path argument | `glob` handler only sent `pattern`, not `path` | Added `path: toolArgs[1]` |
| Tool errors showed raw stack traces | `/tool` endpoint re-threw errors into Hono stream | Return error as text, update ToolPart to error state |
| `stream.write()` not awaited | Hono's `stream.write()` returns Promise | Added `await` to all stream.write calls |
| `opencode run` — oc non-functional | No `Server.listen()` in headless mode | Added `Server.listen({ port: 0 })` in run.ts |
| Bash tool said "DON'T use for file ops" | System prompt conflicted with oc | Rewrote bash.txt with positive oc framing |
| LLM writes scripts to disk | Env vars only available inside bash tool | "Write oc scripts INLINE" in system prompt |
